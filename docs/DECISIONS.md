- D-010 (2026-09-03): **Corn `kc_end` corrected 0.90 → 0.60.** VERIFIED against FAO-56 Table 12 (fao.org/4/x0490e/x0490e0b.htm), not recalled. Table 12 lists **Maize, Field (grain): Kc_ini 0.30, Kc_mid 1.20, Kc_end 0.60–0.35**, with the footnote: *"The first Kc end value is for harvest at high grain moisture. The second Kc end value is for harvest after complete field drying of the grain (to about 18% moisture, wet mass basis)."* And **Maize, Sweet: Kc_ini 0.30, Kc_mid 1.15, Kc_end 1.05**, footnoted *"If harvested fresh for human consumption. Use Kc end for field maize if the sweet maize is allowed to mature and dry in the field."* The previous 0.90 appears in neither row. **0.60 adopted** — the high-grain-moisture row — because a large share of NY grain corn is harvested wet for on-farm storage rather than field-dried (drying is expensive here). **Effect:** the grain-fill ramp interpolates toward Kc_end across gdd_frac 0.62–0.90, where STAGE_WEIGHTS is 1.0 and the MAD factor 0.80 — at gdd_frac 0.76 the coefficient moves 1.025 → 0.875, ~15% lower modelled crop water use through grain fill.   **Two further discrepancies the verification exposed — REPORT ONLY, not changed:**
  - **Corn `kc_mid` is 1.15 in our code; FAO-56 gives 1.20 for field maize.** 1.15 is in fact *sweet corn's* Kc_mid — so field corn is currently carrying sweet corn's mid-season coefficient. This is NOT corrected here because SPEC §4's authoritative worked example is built on `1.15 × 0.28 = 0.322`; changing it would cascade through every worked example and every test asserting them.   **Still open:** corn should arguably be TWO crops — NY splits acreage roughly evenly between grain and silage, which differ in Kc_end (0.60 vs ~1.05–1.15 per the sweet/fresh-harvest logic) and in season length; one `corn` row cannot represent both, and 0.60 is the v1 approximation. Corn maturity days (130, from `stage_days`) still has no agronomic citation.
- D-011 (2026-09-03): **Default planting date is the region's TYPICAL date, not the latest-safe-plant date.** When a farm has not supplied a planting date, stage/Kc/MAD are computed from `NY_TYPICAL_PLANTING` (May 15) rather than `frost_kill_50 − maturity_days`. **Reason:** latest-safe is the last date on which a crop could still finish, so using it as the default assumption models every farmer as having planted as late as possible. A farmer who actually planted May 5 was modelled at ~May 25, losing ~300–400 GDD, landing in an earlier growth stage with a lower Kc and a LESS conservative MAD — an error in the yield-losing direction during pollination. The typical date is clamped so it can never fall after latest-safe (which would imply a crop that cannot mature). Latest-safe is retained as a separate function for planting-window advice, which is its correct use. Implemented in `app/engine/season.py`, used by both `advisor/service.py` and `dashboard/routes.py`.
- D-012 (2026-09-03): **`SECRET_KEY` fails fast instead of defaulting to a placeholder.** `app/auth/routes.py` previously defaulted to the literal `"CHANGE_ME_IN_PRODUCTION"`, so a deploy that forgot to set `SECRET_KEY` silently signed every session token with a publicly known value — an authentication bypass producing no error and no log line. Startup now raises when the key is unset or still the placeholder AND the process looks like a deployment (`FURROWCAST_ENV=production` or `FURROWCAST_COOKIE_SECURE=1`). Local development and the test suite continue to run without the env var, using an explicit dev key. Does NOT address the other two SPEC §6 gaps: `users.phone`/`subscribers.phone` remain plaintext despite "phone encrypted at rest", and sessions remain a single flat 30-day JWT rather than "15-min access, 30-day rotating refresh, device-bound, revocable" — both still open.

  The two that matter most are the depletion fractions. **Onions** and **potatoes** are both shallow-rooted and stress-sensitive; waiting for 50%/45% depletion instead of 30%/35% delays irrigation past FAO-56's no-stress threshold — under-irrigating exactly the crops least able to tolerate it. **Potatoes' root depth was REDUCED** because 30 in exceeded FAO-56's *maximum* Zr, inflating `AW = root_depth × AWC` by ~25% and so understating depletion — the same error compounding in the same direction. Applied in `app/db/seed.py`, `app/engine/kc.py` and migration `m11_fao56_crop_params` (upgrade and downgrade both verified against a real DB).

  **NOT changed — report only:**
  - **`kc_mid` for ANY crop.** Ours vs FAO-56: corn 1.15 vs **1.20**, soy 1.10 vs **1.15**, alfalfa 1.05 vs **0.95**, sunflower 1.10 vs a printed range of **1.0–1.15** (inside it, fine). Corn's 1.15 is load-bearing on SPEC §4's authoritative worked example (`1.15 × 0.28 = 0.322`) and on every stage-weighted example and test derived from it. Note corn's 1.15 is in fact *sweet corn's* Kc_mid — field maize is 1.20 — so field corn currently carries sweet corn's mid-season coefficient. Correcting these needs one coordinated spec-owner decision; doing the non-corn ones alone would leave the table half-migrated.
  - **Root depths BELOW FAO's Zr range**: corn 36 in (Zr 39–67), alfalfa 30 in (39–79), sweet corn 24 in (31–47), cabbage 18 in (20–31). Zr is the MAXIMUM effective rooting depth under ideal conditions; a shallower effective zone is defensible for NY (shallow soils, hardpan, high water tables in muck land) and errs conservative — smaller AW → higher computed depletion → irrigates sooner. Raising them would make the model LESS likely to advise irrigation, which is not a change to make without local rooting data.
  - **corn p 0.50 vs 0.55** and **alfalfa p 0.50 vs 0.55**: ours are MORE conservative than FAO-56. Left as-is.
  - **sunflower p 0.50 vs 0.45**: ours is slightly less conservative. Minor, and sunflower is drought-tolerant. Flagged.
  - **`cover` has no FAO-56 Table 12 entry at all.** Its values (base 40°F, gdd 1200, root 10 in, p 0.45, Kc 0.30/0.60/0.55) have no published reference. Cover crops/green manure are not in Table 12. These are invented and should either be sourced from extension guidance or the crop dropped from the library.
  - `base_temp_f` and `gdd_total` are NOT FAO-56 quantities and were not audited here — they come from GDD/hybrid-maturity guidance and remain uncited (see D-010's note on corn maturity days).

  **Test hygiene:** `tests/test_engine.py` had five tests named *"…parameters match FAO-56 reference values"* that in fact asserted whatever had been typed into `CROP_PARAMS` — four of them pinning values FAO-56 contradicts. - D-015 (2026-09-11): Replace nightly rolling-window moisture initialization with complete planting-to-run replay, carrying water day to day. Unknown planting-day moisture is represented by dry/full endpoints, with the midpoint retained for legacy numeric fields and propagated bounds stored by migration m13. Replaying complete history also incorporates corrected weather/parameters without trusting obsolete saved state. Bounds represent initialization uncertainty only, not empirical confidence intervals. - D-016 (2026-09-22): **A production database may only be selected by an explicit environment variable, never by `.env`.** `app/db/connection.py` called `load_dotenv()` and the repo's `.env` doubles as the Render deployment config — it carries the production Neon `DATABASE_URL`. Because `load_dotenv()` fills in whatever the shell left unset, any command run from `backend/` without an explicit URL silently resolved to **production**: `python -m app.db.seed`, `python -m app.nightly`, `alembic upgrade head`, or any ad-hoc script. Verified before the fix — with both variables unset, the resolved host was the live Neon endpoint. `tests/conftest.py` already guarded pytest against this (added with the test-DB split), but nothing guarded the scripts, which are the ones that write. **Fix:** `connection.py` now snapshots what the real environment supplied *before* `load_dotenv()` runs, and refuses a managed-host URL (`neon.tech`, `render.com`, `amazonaws.com`) that arrived only via `.env`. Render is unaffected because it sets `DATABASE_URL` as a genuine environment variable, which the guard honours. `FURROWCAST_ALLOW_PROD_DB=1` is the deliberate escape hatch. `app/db/seed.py` built its own engine from its own `load_dotenv()` and `alembic/env.py` read `os.environ["DATABASE_URL"]` directly — both now resolve through `connection.resolve_database_url()` so there is one place this decision is enforced. Covered by `tests/test_db_guard.py` (11 cases, including the Render-style production path and the escape hatch). **Not addressed here:** `.env` still holds live production credentials in the working tree; it is gitignored and was never committed, but storing deployment secrets beside the code is what created the hazard. Moving them to a secret manager, or renaming the file so `load_dotenv()` cannot find it, is the durable fix.
- D-017 (2026-09-24): **A failed soil spin-up forces `advice_uncertain`.** Found by running the nightly for 2026-09-22 rather than by reading code: Erie County (36029) lost its Open-Meteo archive fetch to `_ssl.c:993: The handshake operation timed out`, so `om_hist_fail: 1` and `spinup_fail: 1` — yet the run still reported `status: success`, `advisories_generated: 62`, `advisory_errors: 0`, and Erie's advisory read `HOLD` at **90.4%** soil moisture with `advice_uncertain: false` against a **65.1%** statewide average. The county whose data failed to load was the one confidently telling a farmer not to irrigate; with `--sms` enabled that advice would have been texted. **Cause:** `run_pipeline` tracked spin-up failures only as counters (`spinup_ok`/`spinup_fail`) and then called `generate_all(run_date)` with no knowledge of *which* counties had failed, so advisory generation could not distinguish a replayed water balance from an assumed one. D-015's uncertainty machinery keys on unknown *initialization*, which a failed spin-up does not register as. **Fix:** `run_pipeline` collects the failing FIPS and passes them as `generate_all(date, degraded_fips=...)`, which forces `advice_uncertain = True` for those counties before `generate_advisory` runs. This reuses the existing flag rather than adding a parallel concept, so the established consequences — CHECK SOIL in the UI, suppression from SMS — apply unchanged. The run summary gains `advisories_degraded` and `degraded_counties`, which land in the `ingest_runs` payload so a degraded run is visible after the fact. **Not changed:** the `status` semantics in `run_pipeline` still report `success` for a run with degraded counties; whether partial degradation should downgrade the run status is a product question, not an agronomy one. Covered by `tests/test_degraded_spinup.py` (5 cases), including a healthy/degraded pair sharing one synthetic state, an SMS control proving a healthy advisory *is* sent, and an end-to-end test that fails if the pipeline stops passing failures through.
